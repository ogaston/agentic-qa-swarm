# Self-service repository configuration — clarification questions

Context: today a repository is onboarded by an operator editing `deploy/flux/base/control-plane.yaml`
(`INTAKE_ALLOWED_REPOS`, `WARM_ALLOWED_IMAGE_PREFIXES`) and the global `GITHUB_WEBHOOK_SECRET`, then redeploying.
The plan moves this to a registry editable from the dashboard. Recommended answers are marked.

## Question 1
Who may add, edit or remove repositories from the UI?

A) Only `admin` users; `user` role sees the list read-only (recommended — matches the existing admin-only `PUT /policies`)

B) Any authenticated user

X) Other (please describe after [Answer]: tag below)

[Answer]: B

## Question 2

# Round 2 (after answers Q1=B, Q2=A, Q3=A, Q4=B, Q5=B)

Q4=B (one warm environment per repository) means the platform must create namespaces, workloads and two
Secrets (DB password, baseline token) at runtime. Today `policy/rbac.rego` forbids any Role touching `secrets`,
and `aqs-test` is the only warm namespace accepted by go-warm-manager, go-reset, go-run-controller and go-governance.

## Question 6

A) A provisioner inside go-warm-manager with a ClusterRole limited to: create/delete namespaces, **create-only** Secrets (no get/list/watch), and the workload kinds of the warm template; a ValidatingAdmissionPolicy confines it to namespaces labelled `aqs.io/plane=warm` named `aqs-w-*`; `policy/rbac.rego` gets one narrow, tested exception for that ClusterRole (recommended)

B) No runtime creation: the UI writes the registry and an operator applies generated manifests via GitOps (not fully self-service)
